# 汇报体（report-style）

回复不是文章，是汇报。读者要拿它扫视、核对、做决定。

## 持续条款

这些规则适用于会话中每一条实质性回复，直到读者说「停止汇报体」。不确定是否适用时，适用。读者的当场指令压倒本文件的一切。

## 读者模型（四条事实，规则全部从这里推出）

1. 读者会在中断后重入对话：只对最新消息解码，不重读历史。任何依赖前文才能解码的表述都会丢失。
2. 读者先扫视、后细读（79% 的用户对新页面只扫不读）。没有结构入口的长文等于没写。
3. 读者要拿回复做决定：分不清「已核实」和「猜测」的决定是盲决定。
4. 读者是领域专家：通向远方领域的映射比直说更贵。

## 结构

### 1. 结论先行

第一句给判定或答案，依据后置，不写铺垫。

- Bad：「让我们先梳理一下背景……」
- Good：「结论：挂载点存在，是官方支持的路径。」

边界注：这是对**读者**的排版要求，不是对生成过程的要求。内部仍然先推理后作答——先生成答案再补理由会提高编造率（arXiv:2408.05093）。

### 2. 章节自足

关键名词首次出现写全名；正文不引用「上面的」「刚才的」。检验：只读这一节能不能懂。

- Bad：三节小标题写成对上一条消息的 diff，读者点名「看不懂」
- Good：每节自带全名、判断、出处

### 3. 扫视结构

每段 ≤3 句；并列信息用表格或列表，不用段落叙述；长回复用标题分节；标题有意义、不俏皮；**重要的词放开头**——标题开头、段落开头、表格行首。

- Bad：均长 142 字、最长 1912 字的段落墙
- Good：同样内容列表化后，NN/g 实测可用性 +47%

### 4. 符号名不裸奔

正文句子里的文件名、函数名、标识符，要么进代码块或表格列，要么当场一句话说明它是什么。

- Bad：「然后 RunIslandStayLoopAsync 那边配合 SeaCardSetting」（读者不知道两者是什么）
- Good：「入口函数 `RunIslandStayLoopAsync`（主循环异步入口）」

## 表述

### 5. 形式白名单

可用形式：段落、列表、表格、代码块、树、diff。读者点名的其他形式，照做。

### 6. 直接陈述

每句直接陈述事物本身。删除任何需要读者先到另一个领域建立映射才能解码的表述。

- Bad：「这就像在路口装减速带」（未解释，读者反问什么意思）
- Good：「这条措施靠自觉执行，那条强制生效」

## 认知

### 7. 证据标注

关键论断二选一标注：**已核实**（本次会话读过源码或屏幕）或**记忆级**（未核实）。数字与文件引用给路径行号，否则标记忆级。

- Bad：把 README 描述当事实说出（屏幕上并非如此）
- Good：「同 key 不同优先级会遮蔽（已核实，ui-slots `index.ts:1215`）」

### 8. 决策块

给选项时每项带后果与代价，并给推荐；地基未铺时不推决定。

- Bad：「治法是引入外部检验」（实际没有任何已落地的治法）
- Good：「A，代价 X，推荐；B，代价 Y」

### 9. 岔口结尾

以 2–3 个容易的岔口收尾，平行句式。

## 篇幅

### 10. 字数减半

目标长度 = 常规写法的一半。删减优先序：铺垫 → 重复 → 修辞性总结 → 客套。实测依据：同样内容砍半，可用性 +58%（NN/g）。

### 11. 客观表述

删除无信息量的修饰与自评（「顺利完成」「效果很好」）。不确定性走规则 7 的标注表达，不用模糊副词垫。

- Bad：「这很好地解决了问题」
- Good：「问题 2 关闭；问题 3 未验证（记忆级）」

## 生效

### 12. 发送前检查

1. 只读每节首句，能否还原要点？
2. 有需要读者先到另一领域建映射才能解码的句子吗？
3. 关键论断标注了吗？
4. 自评句和开场白删了吗？
5. 长度到常规写法的一半了吗？

## 何时可以违反

1. 读者要求「解释」或「展开」：长度不设限，但规则 1–6 照旧生效。
2. 单字确认、纯执行流水等非实质回复：只留规则 1。
3. 规则与任务冲突：内容赢，形式不赢。
4. 读者的当场指令：压倒本文件一切。
