# 结构图（struct-map）

实施方案是文字。文字描述不了"这些东西怎么连在一起"，而人的认知是从关系长出来的。
所以在写方案的同时，维护一份**结构数据**，右侧栏会把它画成图，人看着图读方案。

图的用途只有一个：**让人在方案还没实施时，就能看见系统的形状并确认它。**

## 一、什么时候建

**建**：方案涉及多个实体（≥4 个方块）且要人做设计确认时。典型场景——新功能、跨模块改动、数据结构调整、权限或状态机。

**不建**：改一个文件的实现细节、修 bug、纯问答、已经有了代码只想画出来看（那是反推图，见第八节）。

## 二、放在哪

```
<工作区>/tmp/structure/<方案名>.struct.json
```

一个方案一份。同一方案后续改动都改这一份，**不要**每次新建带时间戳的文件。
文件名用方案的名字，不用代码里的类名。

## 三、写什么

只有这些字段，没有别的。

```json
{
  "title": "图的名字",
  "groups": [{ "id": "g1", "title": "组名", "note": "一句灰字", "tone": "run" }],
  "nodes": [{ "id": "n1", "group": "g1", "title": "方块名", "sub": "第二行小字", "new": true }],
  "edges": [{ "from": "n1", "to": "n2", "label": "线上两个字", "kind": "分类词", "dashed": true, "new": true }],
  "notes": ["图下方一两句话"]
}
```

- `new: true` 标"本次新增"。**既有的一律不写这个字段**，图上就是灰框；写了就是组色实框。这张图要能一眼分清"已经在那的东西"和"还没做的决定"，所以这个字段别省。
- `new: true` 在边上 = 这条关系本次新增，画成加粗。同样的道理：既有的线不写。
- `kind` 决定线色：同一个 `kind` 同色。**同一类关系务必用同一个词**，否则颜色会被拆散。不写就退回按 `label` 分组。
- `tone`：`run` `state` `warn` `bad` `plain`，只影响组框颜色。
- `dashed`：会失败、可重试、非直接调用的关系用它。

**不要**加坐标、行列号、层号、排序字段——数据里没有布局，布局每次重算。

## 四、从方案里提取什么

1. **方块 = 名词**：会长期存在的东西。会话、配置、缓存、数据库、队列、第三方。动作不是方块。
2. **组 = 一组方块共有的处境**（生命周期、状态性、信任边界）。组不是"模块"，一个人读它应该能答"这些为什么放一起"。
3. **边 = 动词**：谁向谁要东西、谁写给谁、谁通知谁。箭头方向是因果或依赖方向，不是调用栈顺序。
4. **名字用人话**：`文档库` 好过 `DocRepository`。方块第二行可以放代码里的名字，第一行放人的话。
5. **只画点得出来的**：每个方块和每条边，都要有出处（见下）。

## 四之二、两个来源，不能混

图上永远有两种东西，来源相反：

| | 来源 | 证据要求 |
| --- | --- | --- |
| **已经完成的系统** | **读代码**，读真的 | 能指出 `文件:行`。没读过的不要凭印象画 |
| **本次实施设计** | 从方案和意图来 | 能指出方案里哪一句 |

**方向不能反：**

- 既有部分**必须从代码推**。凭记忆、凭命名习惯、凭"一般来说应该有个缓存"画出来的方块，是假图，会让人对着假前提做决定。
- 实施设计**不能从代码推**。代码里没有的东西，只能来自方案；把"代码里现在长这样"当成"所以以后也这样"，就是把现状偷换成设计。

所以在动笔之前要先读一遍相关代码，确认既有部分的真实形状；再读方案，把要改的部分加上去。

方块数控制在 **5~20**。少于此，文字就够；多于 25，人一次读不完。

## 五、怎么更新

**增量，不重写。** 方案每确认一个决策：

1. 找到受影响的方块或边；
2. 改它，或加新的；
3. **保留已有 `id`**——id 变了，人脑里那张图就断了；
4. 决策被推翻的，删掉对应方块/边，不要在图上留"已废弃"。

什么时候必须更新：新增或删除了实体、关系方向变了、某个组多了一样东西、虚线变实线（从"不确定会失败"变成"确定"）。

## 六、自检

改完立刻跑：

```
node <本插件目录>/layout.mjs <那份.struct.json> 750 <临时.html>
```

**退出码非 0 就是有硬规则被触发**，输出会点名是哪条边。必须改到 `violations=0` 再交给用户。

常见违规和处理：

| 输出 | 处理 |
| --- | --- |
| `EDGES_MERGED` | 两条边被画成一条，通常是同一个方块两侧连太多东西，拆组或调整方块顺序 |
| `LINE_IN_FOREIGN_BAND` | 一条长边穿过了中间某个组，说明它跨的组太多了，考虑拆图 |
| `LABEL_ON_BORDER` / `LABEL_LABEL` | 标签太挤，边上的字缩短 |
| `TOO_MANY_CROSSINGS` / `TOO_MANY_EDGES` | 图超出可读上限，见第七节 |

面板里如果出现红条，也是同一个意思：不要忽略它。

## 七、什么时候拆图

- 方块 > 25，或边 > 40；
- 一个组里方块数 > 5（会折行，折行后的连线人很难跟）；
- 出现"某个方块连到几乎所有其他方块"（枢纽），它会把整张图变成放射状。

拆法：按**阶段**拆（改前/改后）、按**层次**拆（数据面/控制面）、或把枢纽单独抽成一张只画它和邻居的图。
拆完的每张图各自独立可读，不要靠"上一张的右半边接这张的左半边"。

## 八、不要做的

- **不要用代码反推实施设计**。要改成什么样，只能来自方案，不能从"现在长这样"推出来。
- **不要凭印象画既有部分**。已有实体和关系必须真的读过代码；读不到就标为不确定，别画成事实。
- **不要画成流程图**。它没有开始和结束，只有谁依赖谁。
- **不要把它当验收清单或追踪表**。方块上不挂状态、不挂负责人、不挂进度。
- **不要和讨论树混为一谈**。讨论树记的是"我们怎么想"，结构图记的是"东西长什么样"。
- **不要为了图好看改方案**。图是方案的镜子；镜子和实物不一致，改实物。
- **不要问用户"要不要画图"**。到条件就画，画完告诉他图在哪。

## 九、和其他产物的关系

| 产物 | 回答什么 | 谁读 |
| --- | --- | --- |
| 实施方案（正文） | 怎么改，按什么顺序改 | 人 + 我 |
| **结构图** | **东西长什么样，谁连着谁** | **人** |
| 讨论树 | 我们讨论到哪、为什么这么定 | 人 + 我 |

三个不能互相替代。方案里不要贴图的文字替代品，图里不要写实施步骤。
